# 更新说明写法

每次发版前在 dev 新建 `docs/release-notes/v<版本号>.md`（版本号与 `curVerBsKeyTools` 一致，如 `v1.4.1.md`）。
`release.yml` 发布时会在前面自动加上安装包说明，再拼上这个文件作为 GitHub Release 正文；**文件缺失或为空会直接让发布失败**。

## 原则

- **写给用户看，不是写给开发看**：说“用户能感知到什么变了”，不说改了哪个函数、哪个文件。
- **一条一件事，一行写完**：动词开头，尽量不超过 30 字；说不清的宁可拆成两条。
- **只写有感知的改动**：CI、文档、换行编码、代码整理、脚本索引自动更新等不写。
- **按重要程度排**：最影响使用的放最前面（崩溃、打不开、数据丢失 > 新功能 > 体验优化）。
- **说现象，不说原因**：写“多屏时窗口打开看不到”，不写“GetDialogPos 返回 -32000”。
- 有对应 issue 的在行尾加 `(#29)`。

## 格式

```markdown
### v1.4.1 更新内容

- 修复：……
- 新增：……
- 优化：……
- BsRetargetTools：……；……
```

- 前缀只用 `修复` / `新增` / `优化` 三种；某个子工具改动多时用工具名做前缀，同一工具的多点用 `；` 连在一行。
- 不写安装包说明（CI 自动加）。

## 怎么整理

1. 列出上个版本以来的提交：

   ```powershell
   git log v<上个版本>..dev --no-merges --pretty=format:"%h %s"
   ```

2. 删掉无感知的（`ci:` / `docs:` / `chore:` / 自动更新脚本索引 / 调试提交）。
3. 同一功能的多个提交合并成一条，按上面的原则改写成用户语言。
4. 自查：不看代码的美术同学能看懂每一条吗？能就提交。

## 已发布版本怎么改

Release 正文发布后仍可修改，不会影响安装包和插件更新：

```powershell
gh release edit v1.4.1 -R AniBullet/BsKeyTools --notes-file <完整正文文件>
```

或在 GitHub Release 页面点编辑。改完记得同步改仓库里的 `docs/release-notes/v<版本>.md`，保持一致。
